# 4. Criptografía: P0 absoluto

Aquí no se negocia.

## Ed25519

Implementar realmente:

* RFC 8032
* key generation
* sign
* verify
* public-key parsing
* malformed key rejection
* signature length validation
* test vectors oficiales

RFC 8032 define Ed25519 y proporciona vectores de prueba y reglas de verificación. ([RFC Editor][1])

### Nunca más:

```text
Real implementation would verify...
```

Ni:

```text
(unsigned — populate via issue())
```

Ni:

```text
return { valid: true }
```

después de solamente parsear.

# 5. JCS

JCS será una dependencia central del core criptográfico.

RFC 8785 define precisamente la representación determinista necesaria para que hash/firma sean reproducibles entre implementaciones. ([RFC Editor][2])

Pipeline:

```text
JSON
 ↓
I-JSON validation
 ↓
JCS
 ↓
UTF-8 bytes
 ↓
SHA-256 / Ed25519
```

Y tendremos vectores:

```text
Node
Python
Rust
```

que produzcan exactamente:

```text
same canonical bytes
same digest
same signature
```

# 14. Proof-of-Possession

Definitivo:

```text
Gateway
   │
   ├── nonce
   ├── audience
   ├── credential_id
   ├── issued_at
   └── expiry
        │
        ▼
      Agent
        │
        ▼
    sign(PoP context)
        │
        ▼
      Gateway
        │
        ▼
   verify public key
```

Debe rechazar:

* nonce reutilizado;
* nonce expirado;
* audience incorrecta;
* credential incorrecto;
* firma incorrecta;
* timestamp inválido.

El nonce store debe ser externo y distribuido en producción.

# 15. Revocación

No mezclar mecanismos arbitrariamente.

El modelo definitivo:

```text
Credential
   │
   ├── status mechanism
   │
   ├── status reference
   │
   └── freshness policy
```

Para VC, Bitstring Status List v1.0 ya es una W3C Recommendation desde mayo de 2025 y está diseñado precisamente para status/revocation de forma eficiente y con propiedades de privacidad. ([W3C][4])

Para ATC:

```text
status list / issuer status endpoint
```

Para formatos externos:

```text
native revocation semantics
```

Y el resultado debe distinguir:

```text
NOT_REVOKED
REVOKED
SUSPENDED
UNKNOWN
UNAVAILABLE
```

**UNKNOWN no es PASS.**

interface TrustAdapter {

  formatId: string;

  parse(input): ParsedCredential;

  validate(parsed): ValidationResult;

    credential,
    context
  ): Promise<VerificationResult>;

Así cada adapter declara qué realmente soporta.

Estoy de acuerdo con **la dirección** del documento, pero hay una cosa que yo no convertiría literalmente en requisito:

Eso debe ser **profile-driven**, no obligatorio en todos los casos.

# Mi conclusión definitiva

**No creo que debamos seguir haciendo pequeños cambios al repo actual.** Hay demasiadas responsabilidades duplicadas y demasiadas afirmaciones que actualmente están adelantadas respecto de la implementación.

El repo actual ya tiene la **idea correcta**, pero necesita una consolidación arquitectónica única:

> **UTS = canonical trust/evidence model**
> **UTA = interoperability**
> **Verification Core = cryptographic truth**
> **Sentinel = evidence generation**
> **Policy Engine = authorization decision**
> **Gateway = enterprise interface**
> **Interceptor = runtime enforcement**
> **MarketNow = commercial control plane**

Y el punto central es éste:

**No añadáis otro adapter, otra feature ni otra capa antes de completar el Verification Core.**

La primera versión verdaderamente seria debe ser capaz de tomar **un ATC v3 real**, verificar su firma Ed25519/JCS, comprobar issuer, key binding, expiración, revocación, PoP, artifact binding y provenance, validar sus evidencias, recalcular su assessment y finalmente emitir una decisión `ALLOW/DENY`. Después ese mismo contrato se aplica a los demás formatos.

La criptografía y el modelo de evidencia se apoyan en estándares existentes —Ed25519 en RFC 8032, JCS en RFC 8785, y provenance/SLSA en sus especificaciones correspondientes— en lugar de inventar primitivas propias. ([RFC Editor][1])

**Éste sería mi baseline definitivo.** A partir de aquí, cualquier cambio futuro debería ser una implementación de este diseño, un bugfix o una actualización obligatoria de un estándar externo; **no otro rediseño de arquitectura**.
